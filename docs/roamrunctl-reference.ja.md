# roamrunctl リファレンス

<p align="center"><a href="roamrunctl-reference.md">English</a> | 日本語</p>

[roamrunctl の README](../Rust/roamrunctl/README.ja.md) を補う、細かい動作と制約の一覧です。鍵の置き場所の 2 つの構成、離れた場所からのペアリング、署名の依頼については README に図があります。この文書では、前提条件、ネットワーク上の制約、例外的な動作を説明します。

マシンの呼び方は README と同じです。

| 呼び方 | 役割 |
|---|---|
| 操作マシン | `look`、`install`、`launch`、`mcp` を実行するマシン |
| 仲介マシン | デバイスと同じ Wi-Fi にあり、離れた場所のマシンのペアリングを仲介するマシン |
| 署名マシン | B で秘密鍵を持ち、接続のたびに署名するマシン。A では操作マシン自身が鍵を持ちます |
| ホスト | `pair introduce --host` で指定する、デバイスとペアリングし、その鍵を保存する側のマシン |

1 台が複数の役割を兼ねることもあります。仲介マシンはペアリングの最初の接続を中継するだけで、ホストの秘密鍵は持ちません。B でも、デバイスの操作は操作マシンとデバイスの間で直接行われ、署名マシンは経由しません。

## インストール

- リリースのアーカイブは、次の 6 つです。
  - `roamrunctl-linux-x86_64.tar.gz`
  - `roamrunctl-linux-aarch64.tar.gz`
  - `roamrunctl-windows-x86_64.zip`
  - `roamrunctl-windows-aarch64.zip`
  - `roamrunctl-macos-aarch64.tar.gz`
  - `roamrunctl-macos-x86_64.tar.gz`
- どのアーカイブにも、バイナリ、README、`SKILL.md`、ライセンス表記が入っています。チェックサムは `roamrunctl-SHA256SUMS` にあります。
- Linux 版のバイナリは静的リンクです。`~/.local/bin` に入れたあと `roamrunctl` が見つからない場合は、そのディレクトリを `PATH` に追加するか、`~/.local/bin/roamrunctl` と指定して実行します。
- Windows 版のアーカイブは、サブディレクトリに展開されます。`.\roamrunctl-windows-x86_64\roamrunctl.exe` のように指定して実行するか、そのディレクトリを `PATH` に追加します。バイナリにコード署名はありません。Windows 11 では、初めて Bonjour で公開したときに、Windows ファイアウォールが通信を許可するか尋ねてきたことがあります。このときは、プライベートとパブリックの両方で許可しました。管理者として実行した PowerShell では、何も尋ねられませんでした。
- macOS 版のバイナリには、Developer ID の署名も公証もありません。`curl` でダウンロードした場合は、`com.apple.quarantine` 属性が付きません。この属性が付いていると、macOS 27 の Apple シリコンの Mac では、起動したとたんに終了させられました。`xattr -d com.apple.quarantine` で属性を外すと、実行できました（README のインストールに、試した手順があります）。
- `cargo install --locked --git ...` には、Rust 1.89 以降と C コンパイラが必要です。これはソースからのビルドで、リリースに含まれる静的リンクの Linux 版とは別のものです。`roamrunctl` は crates.io には公開していません。Homebrew の formula は Homebrew 本体ではなく、`mh-mobile/tap` にあります。
- 表示されるバージョンは RoamRun のバージョンです。同じペアリングに関わるマシンでは、バージョンをそろえてください。0.7.0 より前の `pair introduce` は、`--host` ではなく `--mac` を使っていました。古いリリースが案内するコマンドには、`--mac` と書かれています。

## 最初のペアリングとネットワークの前提

- iPhone / iPad は、Tailscale を入れてデベロッパモードを有効にし、Wi-Fi に接続して、起動後に一度ロックを解除しておきます。モバイル通信でしか届かないデバイスは、新しい接続を受け付けません。
- `pair control --to` は、デバイスと同じ Wi-Fi にあるマシンでペアリングするコマンドです。そのネットワーク上で、Tailscale がデバイスに IPv4 で直接つながっている必要があります。リレー経由や IPv6 では動きません。
- 離れた場所から `pair control --with <仲介マシン>` でペアリングする場合は、次の前提条件があります。仲介マシンはまず、デバイス自身が公開している `_remotepairing._tcp` のサービスを見つける必要があります。デバイスがこのサービスを公開するのは、一度ペアリングしたあとです。一度もペアリングしていないデバイスは、先にデバイスと同じ Wi-Fi にあるマシンでペアリングしてから（Mac の Xcode など）、もう一度仲介を試してください。コマンドの出力では、この最初のペアリングの方法として、仲介マシンでの `roamrunctl pair control --to <デバイス>` も案内されます。ただし、Mac を使わないこの手順は試していません。
- iOS の Introducer アプリを使うと、デバイス自身が仲介役になります。操作マシンで `roamrunctl pair control --with <デバイスの Tailscale 上の名前>` を実行し、アプリに操作マシンの名前を入力します。この場合、仲介マシンは要りません。
- `--to`、`--with`、`--host`、`--for` には、iOS の「設定」に出るデバイス名ではなく、Tailscale 上の名前（`tailscale status` に表示されるもの）を指定します。同じ tailnet のマシンの短い名前か、Tailscale の DNS 名全体で指定できます。複数のマシンに当てはまる名前は拒否されます。

## ポートとファイアウォール

以下に出てくる「オファー」は、ペアリングを始めるためにホストが出すデータです（`--offer` で渡すものと同じです）。

| 操作 | 接続の向き | TCP ポート |
|---|---|---|
| `pair control --to` | デバイス → 操作マシン（Wi-Fi 上） | コマンドが表示する動的なポート |
| `pair control --with` | 仲介マシン → 操作マシン（Tailscale 経由） | 41830。続いて、ペアリング中に表示される別の動的なポート |
| `pair introduce` | デバイス → 仲介マシン（Wi-Fi 上） | 仲介マシンが表示する動的なポート |
| `pair introduce` | 仲介マシン → ホスト（Tailscale 経由） | オファーを要求するときは 41830。続いて、ホストのペアリング用ポート |
| `look`、`install`、`launch`、`mcp` | 操作マシン → デバイス（Tailscale 経由） | デバイスのペアリング用ポート。続いて、その接続のためにデバイスが指定するトンネル用のポート |
| B（`sign --for`） | 操作マシン → 署名マシン（Tailscale 経由） | 41831 |

- `pair control --to` では、デバイスは Wi-Fi 上の自分のアドレスから、コマンドが表示した 1 つの TCP ポートに接続してきます。コマンドはアドレスを 2 つ表示します。このマシンのアドレスと、デバイスのアドレスです。デバイスのほうには「has to be let in」（通す必要がある）と添えてあります。操作マシンのファイアウォールで、この接続を許可してください。Wi-Fi 上で Bonjour / mDNS（UDP 5353）が通ることも条件です。
- ファイアウォールを有効にして実際に試したのは、次の 1 通りです。ufw を有効にした Ubuntu で、試験用のサービスを使った `pair introduce` を、デバイスの代わりに Mac を相手にして実行しました。mDNS は ufw の初期設定のままで通りました。TCP 接続は、`sudo ufw allow proto tcp from <デバイスのアドレス>` を実行するまで応答がなく、実行すると接続できました。表示されたポートだけに絞ったルールは試していません。firewalld など、ほかのツールも試していません。
- `pair control --with` では、指定した仲介マシンから、操作マシンの TCP 41830 と、その回に表示される新しいポートへ接続できるようにします。Tailscale のアクセス制御と、操作マシンのファイアウォールの両方で許可が必要です。動的なポートは、試すたびに変わります。41830 が閉じていると、仲介マシンからは「ホストが待っていない」ように見えます。ペアリング用のポートが閉じている場合は、別のメッセージで知らされます。
- `pair introduce` では、デバイスが仲介マシンの表示したローカルの TCP ポートに接続できることも必要です。`--offer` で Xcode のオファーを渡した場合、ホストの 41830 への問い合わせは行いません。その場合も、ホストのペアリング用ポートには届く必要があります。
- B では、署名マシンが、指定した操作マシンからの TCP 41831 への接続を受け付けるようにします。署名マシンがスクリーンショットや入力を中継することはありません。デバイスとの通信は、操作マシンとデバイスの間で直接行われます。
- macOS では、ファイアウォールを有効にしているとき、`roamrunctl` が外からの接続を受け付けてよいか尋ねられました（Linux のマシンをデバイスの代わりにして、1 回確認）。
- roamrunctl は、Wi-Fi 上の自分のアドレスを、ネットワークインターフェイスのアドレスから選びます。経路表は、そのネットワークに複数のインターフェイスがあるときに、どれを使うかを決めるためだけに使います。ある Windows のマシンでは、「Use Tailscale subnets」の設定によって自分の LAN への経路が Tailscale 経由になっていましたが、ペアリングは問題なく通りました。
- `sign` と `pair control --with` は、このマシンの Tailscale のアドレスで待ち受けます。Tailscale をユーザースペースネットワーキングだけで動かしている環境では、どちらも試していません。

## 時間制限

- `pair control --to`：全体で 7 分です。コードが表示されてから入力するまでは 3 分です。コードを間違えるか、時間切れになると、コマンドは終了します。もう一度実行してください。
- `pair control --with`：仲介マシンからの接続を最大 10 分待ちます。仲介マシンが `roamrunctl` の場合、仲介マシンはペアリングを 5 分待ちます（このマシンは最大 7 分待ちます）。コードが表示されてから入力するまでは 3 分です。デバイスから接続があったものの、ペアリングが成立しなかった場合に限り、このマシンは次の接続を待ち受けます。試行は最大 5 回です。そのたびに、仲介をやり直す必要があります。仲介マシンが時間切れになると、このコマンドは終了します。
- `pair introduce`：Wi-Fi 上への公開は、既定で 5 分です（`--deadline`）。ホストにオファーを要求する場合、`--deadline` に指定できるのは 300 秒までです。その前に、ホストの TCP 41830 を最大 10 分待つことがあります。どちらのマシンのコマンドを先に実行しても構いません。
- `install`：5 分に、1 MB あたり 15 秒を加えた時間が上限です。コマンドは、サイズと上限の時間を表示したあと、終わるまで何も表示しません。MCP のツールは、インストールを始めた時点で答えます（「アプリのインストール」を参照）。デバイスと同じ Wi-Fi で試したとき、3 MB で約 25 秒、37 MB で約 2 分半かかりました。
- `tailscale status`：roamrunctl が尋ねるたびに、答えを 10 秒まで待ちます。`sign` と `pair control --with` は接続のたびに尋ね、答えがなければその接続を断ります。`pair control --with` は、仲介マシンが伝えたデバイスについてもう一度尋ね、答えがなければそこで終わります。

## ペアリング情報とパスフレーズ

- ファイルは、Linux と macOS では `~/.config/roamrunctl/devices` に保存されます。`XDG_CONFIG_HOME` が絶対パスで設定されていれば、`$XDG_CONFIG_HOME/roamrunctl/devices` です。Windows では `%LOCALAPPDATA%\roamrunctl\devices` です（なければ `%APPDATA%`）。デバイスごとに `<名前>.json` が作られ、暗号化した場合は `<名前>.age` になります。
- Linux と macOS では、ディレクトリはモード 0700、ファイルは 0600 で作られます。グループやその他のユーザーに何らかの権限が付いているファイルは、読み込みを拒否します。Windows では、プロファイルのディレクトリの権限に任せていて、同じ確認は行いません。
- 暗号化していない JSON のペアリング情報は、認証情報そのものです。これを読めて、**かつ**デバイスに通信が届くプログラムは、デバイスを使えます。`pair control` と `key import` に `--passphrase` を付けると、ファイルを age のパスフレーズ形式で暗号化します。パスフレーズをコマンドの引数として渡すことはできません。
- パスフレーズは、次の順で、最初に設定されている環境変数から取得します。
  1. `ROAMRUNCTL_PASSPHRASE_FILE`
  2. `ROAMRUNCTL_PASSPHRASE_COMMAND`
  3. `ROAMRUNCTL_PASSPHRASE`
- 設定されている環境変数からの取得に失敗すると、次は試さずに止まります。`ROAMRUNCTL_PASSPHRASE_COMMAND` に指定したコマンドは `sh -c` で実行されます（Windows では `cmd /S /C`）。`ROAMRUNCTL_PASSPHRASE` に入れたパスフレーズは、そのシェルから起動したすべてのプロセスの環境変数に入ります。どれも設定されていなければ、対話的に実行するコマンドは入力を求めます。
- 環境変数から取得するパスフレーズは 1 つで、同じ環境で開いたり保存したりする、暗号化したすべてのデバイスに使われます。`ROAMRUNCTL_PASSPHRASE_COMMAND` のコマンドも、どのデバイスのためでも同じように実行されます。そのため、同じ環境で開くデバイスは、同じパスフレーズにしておく必要があります。たとえば、1 つの `mcp` サーバーは、開くすべてのデバイスに同じパスフレーズを使います。エージェントが動くマシンに鍵を置きたくない場合は、B を使ってください。

| コマンド | パスフレーズの扱い |
|---|---|
| `pair control --passphrase`、`key import --passphrase` | 暗号化したペアリング情報を新しく作るときに、2 回入力を求める。環境変数が設定されていれば、そこから取得する |
| `look`、`install`、`launch` | 暗号化したペアリング情報を開くときに入力を求める。環境変数が設定されていれば、そこから取得する |
| `mcp` | 入力を求められない。暗号化したペアリング情報を初めて開くときに、環境変数からの取得が必要。開いた中身は、ファイルが変わらない間、保持する |
| `mcp --http` | 起動時に、提供する暗号化したデバイスごとに、取得するか入力を求める。開いた中身は、ファイルが変わらない間、保持する |
| `sign` | 起動時に、暗号化したペアリング情報ごとに、取得するか入力を求める |
| `devices`、`devices remove` | パスフレーズは不要 |

- MCP クライアントで使う場合は、README にある登録の設定に加えて、MCP サーバーの環境変数に、上の 3 つのいずれかを設定します。
- macOS で、**対応する項目がすでにキーチェーンにある場合**は、`ROAMRUNCTL_PASSPHRASE_COMMAND` に次のコマンドを指定できます。

  ```sh
  security find-generic-password -a "$USER" -s roamrunctl -w
  ```
- 同じマシンからデバイスをペアリングし直すと、デバイス上の以前のペアリングは置き換えられます。古いペアリング情報では接続できなくなるので、`roamrunctl devices remove <名前>` で削除してください。ペアリングを取り消す場合は、デバイスのデベロッパモードの一覧からも、そのマシンを削除します。
- 接続では、保存してあるポートを最初に試し、続いて 49152〜49167 の残りを試します。デバイスを 2 回再起動し、ネットワークから外して戻したときには、デバイスは毎回 49152 を公開していました。どのポートでも届かない場合は、ペアリングし直してください。
- RoamRun を入れた Mac で鍵を作って、取り込むこともできます。Mac で `roamrun key create <デバイス> device.key` を実行し、操作マシンで `roamrunctl key import device.key` を実行します。取り込みでは、Tailscale 経由でデバイスへの接続を確かめてから情報を保存し、成功すると取り込み元のファイルを削除します。
- `key import` は、別のマシンで roamrunctl が保存した、暗号化していないペアリング情報（`devices/<名前>.json`）も取り込めます。名前は、`--as` を付けなければファイルの中の名前のままです。鍵を別のマシンが持つ情報（B）と、パスフレーズで暗号化した情報（`.age` ファイル）は取り込めません。このマシン自身の devices フォルダにあるファイルは削除しません（`--as` で別の名前にして取り込むと、両方の名前で保存されます）。JSON の前にあるバイト順マークは読み飛ばします。`--passphrase` を付けたときは、デバイスへの接続を確かめる前にパスフレーズを求めます。ファイルの代わりに `-` を渡すと標準入力から読み、何も削除しません。`printf '%s' "$KEY" | roamrunctl key import - --as ci` とすれば、CI のシークレットを、ファイルを介さずに取り込めます。JSON の文字列の外にある改行は意味を持たないので、改行が詰められたり空白に変わったりしたシークレットも同じように読めます。このとき `--passphrase` を付けるなら、標準入力が端末ではないため、パスフレーズは上の環境変数のどれかで渡す必要があります。

## B：署名と信頼関係

B では、署名マシンが秘密鍵を持ちます。操作マシンは、デバイスへ新しく接続するたびに、必要な署名だけを依頼します。

- `roamrunctl sign <デバイス> --for <マシン>` は、指定した Tailscale 上の 1 台にだけ応答します。相手は、tailnet の IP アドレスと、Tailscale のノード ID で確認します。既存のペアリング情報を使った接続検証に必要な形式の依頼にだけ、署名します。新しいペアリングを作るための依頼には署名しません。依頼は 1 つずつ処理します。
- `sign` は、起動時に、指定したデバイスのペアリング情報を読み込みます。実行中に削除されたり、置き換えられたりした情報には、それ以降署名しません。新しい情報で署名するには、`sign` を再起動します。
- 既定では、操作マシンは**オンラインで、タグがなく、同じ Tailscale ユーザーのもの**であるマシンから署名マシンを探します。操作マシン自身にタグが付いていないことも条件です。この方法は、信頼できる tailnet では手軽です。ただ、ほかの人の動かすマシンが混ざる環境では、これに頼らないでください。
- 次のいずれかにあたる場合は、**デバイスを初めて使う前に** `ROAMRUNCTL_SIGNER=<署名マシンの Tailscale 上の名前>` を設定してください。
  - どちらかのマシンにタグが付いている場合
  - 2 台が別のユーザーのものである場合
  - 別のマシンも同じデバイス名で `sign` を実行できる場合

  Linux / macOS での例です。

  ```sh
  export ROAMRUNCTL_SIGNER=home-pc
  roamrunctl devices
  roamrunctl look phone
  ```

  PowerShell では `$env:ROAMRUNCTL_SIGNER = 'home-pc'` です。エージェントから使う場合は、MCP サーバーの環境変数に設定します。
- B の構成でデバイスを初めて使うとき、`roamrunctl` は、どの署名マシンがどのデバイスを担当するか（以下、署名マシンとの対応）を保存します。**秘密鍵は保存しません。** 以後は、この対応でしか使いません。署名マシンを指定していない場合は、同じユーザーのマシンのうち、その名前のデバイスに署名できると応答したマシンを信用します。2 台が応答した場合は、Tailscale 上の名前が辞書順で先のほうを選びます。信頼できないマシンが混ざる環境では、自動で探す方法に頼らないでください。対応を保存できない場合、そのデバイスは使いません。
- **操作マシン**で `roamrunctl devices remove <名前>` を実行すると、保存した対応が消えます。署名マシンにある秘密鍵は**消えません**。同じ 1 台のデバイスに対して 2 台の署名マシンが別々のペアリングを持つ場合は、それぞれ別の名前で保存しておく必要があります。
- 署名の仕組みでは、秘密鍵が操作マシンに送られることはありません。ただし、**これでできる操作が制限されるわけではありません。** `sign` が応答している間、許可された操作マシン上のどのプログラムでも、デバイスへの接続を開けます。接続したセッションでは、画面の確認、入力の送信、アプリのインストールができます。`sign` を止めると**新しい**接続には署名されなくなりますが、すでにある接続（開いたままの MCP の接続など）は切れません。`sign` は、署名した接続を 1 つずつログに出します。タップやスクリーンショット、インストールのたびに承認を求めるものではありません。
- 接続済みの操作マシンから、デバイスに新しいペアリングを追加できるかどうかは、**試していません**。そのため、B なら操作マシン上のソフトウェアが恒久的なアクセスを得ることはない、とは言えません。

## MCP のツール

- `roamrunctl mcp` は、標準入出力で通信します。`--http` を付けると HTTP で通信します（次の節）。MCP の `look` は JPEG の画像をエージェントに返し、単体の `roamrunctl look` コマンドは PNG を保存します。どちらも、画像の長辺は最大 1280 ピクセルです。
- MCP の `look` は id を答えます。`tap`、`swipe`、`pinch`、`type`、`paste` には、その id を渡します（`"look": 12`）。`look` が使えるのは 60 秒の間で、そのデバイスの最新の `look` である間だけです。どのクライアントのものでも、あとにほかの `look` があれば（失敗したものも含む）、その `look` は使えなくなります。`press`、`elements`、`install`、`launch` があったときも同じです。デバイスに届いたかどうか分からない失敗があったときや、同じ名前でほかのデバイスが保存されたときも、使えなくなります。`tap`、`swipe`、`pinch` に使えるのは **1 回**だけです。`tap`、`swipe`、`pinch`、`type`、`paste` のどれかに使ったあとは、次の `tap`、`swipe`、`pinch` に新しい `look` が要ります。`type` と `paste` には続けて使えるので、`look` → 入力欄を `tap` → `type` の流れは `look` 1 回で済みます。id は起動のたびにランダムな数から始まるので、前に動かしたときの id を、あとの `look` と取り違えることはありません。
- PNG の `look` では、そのあとにデバイスの向きが変わると、`tap`、`swipe`、`pinch` は拒否されます。変化は、デバイスが報告する向きか、画像の縦横から検出します。デバイスが向きを報告しない場合は、検出できる**とは限りません**。`tap`、`swipe`、`pinch` の座標は、直前の `look` が返した画像のピクセルで指定します。
- `pinch`（0.13.0 以降）は、`x`、`y` を中心に 2 本の指を置き、指の間隔が始めの `scale`（0.25〜4、既定は 1）倍になるまで動かしてから離します。`degrees`（−180〜180、既定は 0）を渡すと、その角度だけ時計回りに回します。かける時間は `milliseconds` で指定します（50〜5000、既定は 500）。始めと終わりのうち広いほうの間隔は、画面の短い辺の 40% です。指が画面の外に出る場合は、位置を動かさずに断り、`look` はそのまま使えます。`scale` が 1 で回さなければ、2 本指のタップになります。回す向きは、デバイスをどちらに向けていても、`look` の画像の上での時計回りです。2026-11-04 に、macOS の標準入出力の `mcp` から、開いた状態の iPhone Duo 1 台で試しました。Google マップでは、`scale` 1 で 1 段階縮小し、2 で拡大し、0.5 で縮小しました。`degrees` 45 では地図が時計回りに回りました。端に近すぎる点は断られ、その `look` で次の swipe が通りました。写真では、`scale` 2 で拡大しました。5000 ms の `pinch` の途中で Ctrl-C を押すと `stopped:` と答え、すぐあとの 2 本指のタップで縮小しました（指は残っていませんでした）。
- `type`、`paste`、`press` は、そのとき画面でフォーカスのあるものに作用します。`press` は `look` に縛られません。`paste` を実行すると、デバイスは毎回「ペーストを許可」と尋ねます。`type` と `paste` は、`look` と同じく、直前の入力から 1 秒たつまで待ってから送ります。入力欄を tap した直後に送ったキーが、落ちたり、カーソルの前に入ったりしたためです。
- 各ツールには、MCP の `readOnlyHint` と `destructiveHint` を付けています。読むだけのツールとしているのは、`devices`、`look`、`install_status` です。`elements` は、どちらでもありません。画面をスクロールさせることはありますが、何かを消すことはないためです。残りのツールは、破壊的な操作としています。押したものや入力した文字は、手で操作したときと同じように働きます。たとえば、タップで削除や送信をすることもあり、入力した改行は Return になります。`press` の `lock` はここから取り消せません。`launch` は実行中のアプリを先に終了させ、`install` はアプリを置き換えます。この印をどう扱うかはクライアントしだいで、実際のクライアントでの動きは確かめていません。
- `elements` は、要素ごとにキャプションを 1 行で答えます。アプリがアクセシビリティ識別子を付けた要素では、行の末尾に ` — id: <識別子>` が付きます（`com.apple.settings.airplaneMode` など）。識別子は、iPhone Duo の設定アプリでデバイスが送ってきたものから確かめました。読んだ 5 つの要素には、どれも識別子がありました。2026-11-06 に、同じ iPhone Duo を Wi-Fi でつないで試しました。設定アプリでは 12 行すべてに識別子が付き、ウィジェットの画面では、検索のウィジェットの要素はキャプションだけでした。デバイスが送ってきたものに位置がなかったので、位置は答えません。
- 実行待ちの呼び出しは、始まる前に取り消されれば実行されません。すでに実行中の呼び出しは、最後まで実行されることがあります。MCP サーバーは接続を開いたまま保ち、保存した対応が変わったときや、接続が切れたときには、デバイスに接続し直します。
- macOS では（0.11.0 以降）、`look`（MCP の `look` と `roamrunctl look`）は、デバイスの画面のストリームから画面を取り、このマシンでデコードします。デバイスがフルサイズの PNG を作るのを待ちません。iPhone Duo を LAN の中で使い、写真を表示した画面では、`look` 1 回がこの方法で約 1.2 秒、PNG では 10〜36 秒でした。ストリームが動いている間、デバイスには画面共有として表示され、デバイスを使っている人にも見えます。最後の `look` か操作から約 5 秒たつまで続きます。その間、アプリによっては音が聞こえなくなります。RoamRun の `look` のときと同じです（[sound-while-looking.md](sound-while-looking.md)、英語）。画像はディスプレイ本来の向きで返ります（横に持った iPhone Duo では縦長。確認済み）。`tap`、`swipe`、`pinch` は、その場合も画像のピクセルで指定します。`look` のあとにデバイスの向きが変わっても、確かめません。電話や VoIP の通話中は、デバイスがストリームを断り（VoIP の通話中に確認）、`look` は PNG になります。デバイスが画面の大きさを答えないときや、フレームがその大きさに合わないときも、PNG を使います（切り取れないフレームでは、位置がずれるためです）。そのときは、MCP の `look` の答えにそう書きます。`ROAMRUNCTL_LOOK=screenshot` を設定すると、0.11.0 より前と同じく、いつも PNG を使います。ほかの値は、何かをする前に断ります。`mcp` と `roamrunctl look` は、Ctrl-C で止まるとき、`look` が残したストリームを止めてから終わります。
- Linux と Windows では、`look` はデバイスの PNG です。デバイスに画面共有のセッションは表示されません。画面と入力を試している間、音楽は再生されたままでした。マイクや、そのほかの一部の操作については確かめていません。

## HTTP で使う MCP

次の形で起動し、Ctrl-C で止めるまで動きます。

```
roamrunctl mcp --http <ポート> --allow <相手> [--allow <相手>…] [--token-file <ファイル>] [--allow-install [--max-upload <MiB>]] <デバイス>…
```

- 待ち受けるのは、このマシンの Tailscale の IPv4 アドレスだけです。Tailscale が動いていないとき、`--allow` がないとき、デバイスの指定がないとき、root で動かしたときは起動しません。root かどうかは、Linux と macOS では実効ユーザーで判断します。Windows では確かめません。次のデバイスも指定できません。署名するマシンが提供しているだけで、まだこのマシンで使ったことのないもの、保存ファイルを読めないもの（パスフレーズが与えられていない場合など）、同じデバイスを 2 つの名前で指定したものです。
- 呼び出せる相手は、呼び出し元のアドレスについて `tailscale whois` が答える内容で決めます。要求のたびに尋ねます。5 秒以内に相手が分からなければ、その要求には 503 を返します。やり直せば通ることがあります。`--allow tag:<名前>` はタグの付いたマシンをそのタグで、`--allow <ログイン名>` はタグのないマシンをその持ち主のログイン名で許可します。ログイン名が、タグの付いたマシンに当てはまることはありません。ほかの Tailnet から共有されたマシンは断ります。このマシン自身からの呼び出しも、トークンがなければ断ります。
- `--token-file` を付けると、どの要求にも `Authorization: Bearer <トークン>` が必要になります。ファイルは持ち主だけが読めるものでなければなりません（Windows では確かめません）。トークンは 1 行で、32 文字以上です。
- 通信の形は、MCP の 2025-11-25 の Streamable HTTP です。`POST /mcp` 1 回で JSON-RPC のメッセージを 1 つ送り、JSON で答えます。通知と応答には 202、`GET` と `DELETE` には 405 を返します。セッションは、呼び出しを取り消すためだけに使います（後述）。呼び出しの前に `initialize` は要りません。`MCP-Protocol-Version` を送る場合は、2024-11-05、2025-03-26、2025-06-18、2025-11-25 のどれかです。それ以外なら 400 を返します。
- 次のものには、ほかの処理より先に答えます。`/.well-known/*` と `/register` には 404 です（ここに OAuth はありません）。`Origin` が付いた要求には 403 です。`Host` が、このマシンのアドレスでも Tailscale の名前でもない（ポート付きで。ポートが 80 なら、ポートのないものも受けます）要求には 400 です。そのあと、トークンがないか違えば 401（`WWW-Authenticate: Bearer`）、`tailscale whois` で相手が分からなければ 503、許可のない相手には 403 を返します。
- 1 つの接続で受ける要求は 1 つです（`Connection: close`）。ヘッダは接続から 10 秒以内に、本体はそこからさらに 30 秒以内に、届き終わらなければなりません。少しずつ送られてきても延ばしません。本体は、chunked と書かれていれば chunked として（長さが一緒に付いていても）、そうでなければ長さどおりに読みます。上限は 1 MB です。同時に受ける接続は 32 まで、1 つのアドレスからは 17 までで、それを超えると 503 を返します。
- 1 台のデバイスへのツールの呼び出しは、標準入出力のときと同じく 1 つずつ順に実行します。順番はデバイスごとなので、あるデバイスへの呼び出しが、ほかのデバイスへの呼び出しを待つことはありません。順番が来たときに、呼び出し元が接続を閉じていた（自分の側だけ閉じた場合も含む）か、接続が切れていた呼び出しは実行しません。`initialize` には `Mcp-Session-Id` を付けて答えます。クライアントは、以後の要求にそれを付けて送ります（MCP の SDK はそうします）。それを付けた `notifications/cancelled` は、そのセッションの、その id の呼び出しを、順番が来る前なら取り消します。取り消しのほうが呼び出しより先に届いた場合も同じです（取り消しは 1 分間、同時に 256 件まで覚えておきます）。セッションのない取り消しは何もしません。要求の id はクライアントが選ぶもので、ほかのクライアントの呼び出しが同じ id を持つことがあるためです。その場合は、接続を閉じれば取り消せます。なお MCP 2025-11-25 は、接続が閉じたことを取り消しとみなさないよう求めていますが、ここでは、いなくなった呼び出し元のための操作はしません。順番を 20 秒待った呼び出しは、実行せずに「not begun」と答えます。ツールの呼び出し以外には、すぐ答えます。
- 1 つのサーバーを、複数のエージェントが同時に使えます。`tap`、`swipe`、`type`、`paste` は、どの `look` に対するものかを id で示し、そのデバイスにあとから `look` があれば、誰のものでも断ります。
- `devices` の一覧に出し、操作できるのは、指定したデバイスだけです。それも、起動したときの保存のままである間だけです。削除されたり、同じ名前で保存し直されたりしたデバイスは、起動し直すまで使いません。`install` と `install_status` は、`--allow-install` を付けたときだけ使えます。そのときの `install` は、パスではなくアップロードを受け取ります（次の節）。
- 要求ごとに 1 行を、標準エラー出力に記録します。時刻（UTC）、呼び出し元のアドレスと Tailscale が答えた相手、メソッドとツール、結果、かかった時間です。制御文字は `?` に置き換えます。トークン、要求の本体、入力・貼り付けした文字、画面の文字、画像、アップロードの中身は記録しません。

### アップロード（`--allow-install`）

- `PUT /upload` は、本体として `.ipa` を受け取ります。長さは `Content-Length` でも chunked でもかまいません（`curl -T app.ipa`）。答えは `{"upload": "<id>", "size": <バイト数>, "sha256": "<16進>"}` です。`install` には、この id と sha256 を渡します（`{"device": …, "upload": "<id>", "sha256": "<16進>"}`）。`--allow-install` がないときは、`/upload` は 404 で、`install` も `install_status` も一覧に出ません。
- 呼び出し元を確かめたあと（`/mcp` と同じです）、次の順に断ります。`PUT` 以外は 405、長さがなく chunked でもなければ 411 です。長さが上限を超えていれば、`100 Continue` を送る前に 413 を返します。ほかのアップロードを受け取っている最中なら 409 です。上限は `--max-upload <MiB>` で決めます。既定は 1024 で、1 から 4096 まで指定できます。本体は届き続ける必要があります（0.11.0 以降）。かけてよい時間は 30 秒に、届き始めた 1 MiB ごとに 2 秒を足したもので、申告した長さでは決まりません。途中で 60 秒何も届かないときも含めて、間に合わなければ 408 で断り、アップロードの枠を空けます。chunked の最後のかけらのあとに続く行は、`/mcp` と同じく 64 行、8 KiB までで、超えると 431 です。
- 保持するアップロードは 1 つです。次のアップロードが届き始めると、どの呼び出し元のものでも、保持していたものは捨てます。置き場所は、この起動のためにシステムの一時フォルダの中に作るフォルダです。フォルダは 0700、ファイルは 0600 で作ります。Windows では、そのユーザーの一時フォルダの中に作り、それ以上の制限はかけません。途中で切れたものはすぐ捨て、30 分使われなかったものも捨てます（1 分ごとに見ます）。Ctrl-C、SIGTERM、SIGHUP のどれで止めても、フォルダごと消します。Windows では、Ctrl-C と Ctrl-Break のとき、コンソールを閉じたときに消します。それ以外の止まり方（強制終了など）では、フォルダが残ります。
- アップロードをインストールできるのは、それを送った呼び出し元だけです。呼び出し元は、`tailscale whois` が答えるノードの変わらない id で見分けます。sha256 は、アップロードの答えと同じでなければなりません（大文字と小文字は区別しません）。ほかの呼び出し元の id や、違う sha256 は、順番を待つ前に断り、アップロードは残します。
- 1 つのアップロードで、インストールは 1 回です。まず中身を検査します（次の節）。デバイスを開けなければ、アップロードは残るので、あとでやり直せます。デバイスを開けたら、インストールがアップロードを受け取り、終わったときにファイルを消します。

### `install --relay` と `launch --relay`

呼び出す側のマシンで次のように実行すると、自分で保存したデバイスではなく、このサーバーを通してデバイスを使います。relay は、デバイスの鍵を持ち、`mcp --http` を動かすマシンです。tailnet のどこにあってもかまいません。ほかの操作マシンと同じく Tailscale 経由でデバイスにつなぐので、デバイスのそばに置く必要はありません。

```sh
roamrunctl install <デバイス> <app.ipa> --relay <アドレス>:<ポート> [--token-file <ファイル>] [--timeout <秒>] [--launch]
roamrunctl launch <デバイス> <bundle id> --relay <アドレス>:<ポート> [--token-file <ファイル>]
```

- `<デバイス>` は、relay の `mcp --http` に指定した名前です。`--relay` には、アドレスとポート、またはサーバーが表示したアドレス（`http://<アドレス>:<ポート>/mcp`）を渡します。`ROAMRUNCTL_RELAY` でも指定できます（空の値なら指定なしとみなします）。どちらかがあると、`install` と `launch` は、呼び出す側のマシンに保存したデバイスを使いません。名前を渡した場合は、名前から得た IPv4 アドレスを順に試します。サーバーは IPv4 でしか待ち受けないからです。`ROAMRUNCTL_PROXY` が指すプロキシを通すときは（次の節）、名前をそのままプロキシに渡し、プロキシが名前を引きます。`http_proxy` などは使いません。
- トークンは `--token-file` で渡します（サーバーと同じく、所有者だけが読めるファイルで、1 行に 32 文字以上）。なければ `ROAMRUNCTL_TOKEN` を使います。どちらもなければ、トークンを送りません。
- `install` が受け付けるのは `.ipa` だけで、`.app` フォルダは受け付けません。`.ipa` は、`install` と同じように検査します（次の節）。そのあと、1 つのプロセスから次の順に進めます。relay は、アップロードとインストールが同じ Tailscale のノードから来ることを求めるからです。まず `Expect: 100-continue` を付けて `PUT /upload` を送ります。トークンがないなどで断られる場合は、`.ipa` を送る前に分かります。relay が答えた sha256 をファイルのものと比べ、違えば何もインストールせずに止まります。次に `install` でそのアップロードを指定し、`install` が答えたインストールの id を付けて、`install_status` を 5 秒ごとに尋ねます。アプリが入ったか、入らなかった理由が返るまで続けます。表示するのは `install_status` の答えです。`install` が id を答えない relay（0.9.0 より前）なら、インストールを始めたところで止まります。`Expect` に 10 秒たっても答えないサーバーには、そのまま本体を送ります。そのあとに届いた 100 Continue は読み飛ばします。本体を送っている途中で断られた場合も、サーバーの答えを読みます。`--launch` を付けると、`install_status` の答えを表示してから、`.ipa` の中の bundle identifier でアプリを起動します。
- relay が 503 を返した要求は、3 秒おきに最大 5 回まで送り直します。それ以外で断られたら、ステータスと relay の答えを表示して止まります。401 はトークンの問題、403 は relay の `--allow` で許可されていないこと、`/upload` の 404 は `--allow-install` がないことを表します。要求ごとに接続を 1 つ使います。`launch --relay` は、503 の送り直しも含めて、全体で最大 120 秒待ちます。`install --relay` は、期限（`--timeout`、次の項目）まで待ちます。その間も、1 回の読み書きで待つのは最大 120 秒です。どちらも、そこであきらめたときは「no answer within 120 s」と表示します。
- `--timeout <秒>` は、アプリが入るまでコマンド全体で待つ最大の時間です。アップロードと、その間の各要求も含みます。過ぎたら何も送らず、答えも待ちません。1 バイトずつ答える relay、途中で止まる relay、1xx を送り続ける relay でも同じです。送っている途中のアップロードも止めます。既定は、relay がインストールに与える時間（5 分に、1 MB あたり 15 秒を足した時間）が基本です。これに、アップロードの分の 1 MB あたり 2 秒と、さらに 1 分を足します。過ぎるとコマンドは失敗します。始まっていたインストールは relay で続くので、どう終わったかは relay の `install_status` で分かります。

### `ota --server`

```sh
roamrunctl ota <app.ipa> --server <アドレス>:<ポート> [--token-file <ファイル>] [--replace] [--timeout <秒>]
```

0.12.0 以降です。Mac の **OTA server** を通して、`.ipa` を OTA のページに載せます。OTA server は、RoamRun が動いている Mac で、`--allow-ota` を付けて動かす `roamrun mcp --http` です（[ota.ja.md](ota.ja.md#ci-のジョブから)）。OTA server は relay ではありません。relay（`roamrunctl mcp --http`）はページに載せられず、OTA server はデバイスを操作しません。

- `--server` には、アドレスとポート、またはサーバーが表示したアドレスを渡します。環境変数では指定できません。トークン、名前の引き方、`ROAMRUNCTL_PROXY` の扱いは、`--relay` と同じです。
- 何かを送る前に、サーバーが何かを尋ねます（`initialize` と `tools/list`）。relay なら、relay だとして断ります。`ota` のないサーバー（0.12.0 より前の RoamRun か、`--allow-ota` なしで起動したもの）も、そう言って断ります。ファイルは `.ipa` である必要があります。署名を確かめるのはサーバーです。
- そのあと、1 つのプロセスから次の順に進めます。まず `PUT /upload` を送ります。ほかのアップロードを受け取っている最中で 409 が返る間は、3 秒おきに送り直します。サーバーが答えた sha256 をファイルのものと比べます。最後に、アップロードと `replace` を渡して `ota` を呼びます。表示するのは `ota` の答えで、ビルドが保存されたら終了コードは 0 です。保存できても、まだページには出ていません。RoamRun のアプリが動いていれば、30 秒ほどでページに出ます。
- `ota` が「そのアップロードはない」と答えた場合は、ファイルを 1 回だけ送り直します。別のジョブのアップロードに置き換えられた場合で、`ota` が動く前に断られるので、何も保存されていません。2 回目も同じなら、そう表示して止まります。同時に公開するジョブは、失敗することがあります。ビルドが拒否されたら、サーバーの答えを表示して止まります。`ota` の答えが届かなかったときは、送り直しません。ビルドが保存されている場合があるからです。
- `--timeout <秒>` は、ネットワークの処理で待つ最大の時間です。尋ねる要求、アップロードとその送り直し、`ota` が含まれます。1 回の読み書きで待つのは最大 120 秒です。sha256 のためにファイルを読む時間と、名前を引く時間は含みません。既定は、1 MB あたり 2 秒に、30 秒と、サーバーの検査の分の 120 秒を足した時間です。

## ブラウザで画面を見る（`view`、試作）

```
roamrunctl view <デバイス> --http <ポート> --allow <相手> [--allow <相手>…] [--token-file <ファイル>] [--at <アドレス>] [--mcp] [--https <ポート>]
roamrunctl view --usb [<UDID>] --http <ポート> --allow <相手> …
```

Ctrl-C で止めるまで動きます。自分のデバイスを家に置いたまま、tailnet のほかの場所からブラウザで見て操作するための試作です。2026-11-05 に、iPhone Duo（iOS 27）と Chrome で試しました。デバイスが送るパケットは途中で欠けることがあり、欠けると次のキーフレームまで画像が止まります。30 秒のうちに欠けた回数は、自宅の Wi‑Fi のアドレスでデバイスにつないだときは 1〜3.5 回でした。Tailscale を通したときは 38 回でした（別の回では 70 秒で 12 回）。

使い方の要点は次のとおりです。デバイスをつないだ Mac で動かします。つなぎ方は USB（`--usb`）か同じ Wi‑Fi（`--at`）で、Tailscale は通しません。`--token-file` も付けます。その Mac では `http://localhost:<ポート>/` を開きます。tailnet のほかのマシンからは、さらに `--https <ポート>` を付けて起動し、表示された HTTPS のアドレスを開きます。ブラウザは HEVC を復号できる必要があります（試したのは Mac の Chrome と iPhone の Safari です）。デバイスへの接続が切れたら、view を起動し直します。音が出るのは、Mac で動かしたときだけです。

- このマシンの Tailscale の IPv4 アドレスで待ち受けます。`--token-file` を付けたときは、ループバックでも待ち受けます。`/` でページを、`/ws` で WebSocket を受けます。`mcp --http` と同じく、Tailscale が動いていないとき、`--allow` がないとき、root で動かしたときは起動しません。`--allow` と `--token-file` の読み方も同じです。
- ページは HEVC の映像を WebCodecs の `VideoDecoder` で復号します。この Mac では `http://localhost:<ポート>/`、別のマシンでは `--https` が表示する HTTPS のアドレスで開けます。どちらも安全なページとして扱われ、T3 Code などの組み込みブラウザでも使えます。ただし、そのブラウザが HEVC に対応している必要があります。iPhone 15 Pro の Safari では、tailnet の HTTP アドレスでも映像が出ました。Chrome では HTTPS、localhost、または `--unsafely-treat-insecure-origin-as-secure` の指定が必要です。復号できない場合、ページには理由と開き方を表示します。
- tailnet の HTTP アドレスに直接つないだ相手は、接続ごとに `tailscale whois` で調べます。ページの接続と、WebSocket を受ける前の接続です。次の順に断ります。`Host` がこのサーバーのアドレスでも Tailscale の名前（ポート付き）でもなければ 400 です。`Origin` がこのサーバー自身のものと違えば 403 です。ページは `Origin` なしでも受けますが、WebSocket には必要です。`GET` 以外は 405、ほかのパスは 404 です。`tailscale whois` で相手が分からなければ 503、許可のない相手には 403 を返します（ページへの 403 には、理由を文字で書きます）。このマシン自身からは、`--token-file` を付けたときだけ受けます。トークンは URL には入れません。ページが尋ね、WebSocket の最初のメッセージで送ります。違うトークンや、必要なのに付いていないときは、1008 で WebSocket を閉じます。
- 同時に受ける接続は 12 まで、1 つのアドレスからの 1 つの入り口では 6 までです。Tailscale のアドレス、このマシンの localhost、`tailscale serve` 用のループバックは、別々に数えます。ページは 2 本、MCP のクライアントは 2〜3 本を使います。それを超える接続は、答えずに閉じます。受け入れる前の相手には、ヘッダ、ページの最初のメッセージ、MCP の要求の本文を、1 回の読み込みでも全体でも 10 秒まで待ちます。ページには 5 秒ごとに ping を送ります。ブラウザから 20 秒何も届かなければ（pong も受け取りの知らせもなければ）、そのページはなくなったものとして切ります。ブラウザは、裏に回したタブでページのスクリプトが止まっていても ping に答えます。送ったものの受け取りが遅いだけでは切りません。
- `--token-file` を付けると、このマシンのループバックでも、`http://localhost:<ポート>/` で待ち受けます。付けなければ、このマシンからは見られず、起動のときにそう表示します。ブラウザは `localhost` のページを安全なページとして扱うので、起動のときの設定を付けられないブラウザ（コーディングエージェントのアプリに組み込まれたものなど）でも、ここなら画像が出ます。T3 Code のブラウザでは、ここで `VideoDecoder` が使え、Tailscale のアドレスでは使えませんでした。ここから来る相手はこのマシン自身として扱い、Tailscale には尋ねません。トークンが要ります。
- `--https <ポート>`（`--token-file` が必要です）を付けると、ページを HTTPS でも出します。アドレスは `https://<このマシンの Tailscale の名前>:<ポート>/` です。localhost 用とは別のループバックで `tailscale serve` からの接続を受け、Tailscale の証明書を使います。tailnet のどのブラウザでも、アプリに組み込まれたものでも、安全なページになります（T3 Code のブラウザでは、ここで `VideoDecoder` が使えました）。
- `--https` のポートを `tailscale serve` がもう使っていれば、断ります。`tailscale serve` のほかの設定は、そのままにします。Ctrl-C で、そのポートの分だけを外します（強制終了したときは残るので、`tailscale serve --https=<ポート> off` で外します）。`tailscale serve` を通った要求には、だれのものか（`Tailscale-User-Login`）が付いています。そのログイン名を `--allow` で確かめます。ログイン名がなければ、トークンが正しくても断ります。タグ付きのマシンは、`--allow tag:<名前>` を指定した tailnet の HTTP アドレスを使います。HTTPS では、許可したログイン名とトークンの両方が必要です。ポートが 443 なら、アドレスの `:443` は省略できます。
- `--at <アドレス>` を付けると、保存したときのアドレスではなく、そのアドレスでデバイスにつなぎます。このマシンと同じ Wi‑Fi でのデバイスのアドレスを渡せば、ストリームは Tailscale を通りません。デバイスを開くのは、これまでどおりペアリングです。ページは変わらず Tailscale のアドレスで出します。ほかのマシンが署名するデバイスには、`--at` なしの `view` で一度開いてから使えます。デバイスで動画を流しながら `--at` 付きで 30 秒ずつ 2 回測ると、欠けたのは 6 回と 13 回でした（パケットの約 3 %）。その間に Tailscale を通して測った 2 回は、19 回と 56 回でした（8 % と 58 %）。
- `--usb` を付けると、保存したデバイスではなく、このマシンに USB でつないだデバイスを使います。usbmuxd を通し、このマシンのシステムがそのデバイスと持っているペアリング（デバイスがこのマシンを信頼していること）でつなぐので、roamrunctl でのペアリングは要りません。USB で複数つないでいるときは、`--usb <UDID>` で 1 台を選びます。iPhone Duo で動画を流しながら USB で 30 秒ずつ 2 回測ると、欠けたパケットはありませんでした。その間に `--at` で測った 2 回は、欠けが 26 回と 12 回でした（パケットの 43 % と 14 %）。最初の画像が出るまでは、USB で 0.2 秒、Wi‑Fi で約 1.1 秒でした。試したのは macOS だけです。
- `--mcp`（`--token-file` が必要です）を付けると、`POST /mcp` で roamrunctl の MCP のツールも出します。このデバイスに、この接続のまま使います。人が見ている間に、tailnet やこのマシンのエージェントが操作するためのものです。確かめ方は `mcp --http` と同じです。`Origin` のある要求は断り、トークンを `Authorization: Bearer` で受け、`--allow` で相手を見ます。ツールは `mcp --http` と同じで、install はありません。扱うのは 1 台だけで、その名前は `devices` が答えます（保存した名前か、`--usb` ならその UDID、指定がなければ `usb`）。
- `--mcp` の look は、このストリームから画像を取ります。次のキーフレームを求め、パラメータセットのそろったものが届くのを待ちます。それをここで復号し（macOS）、画面そのままの向きで返します。ページを開いていなくても、そのためにストリームを動かし、数秒後に止めます。8 秒のうちに届かないときや macOS 以外では、デバイスの PNG を使い、その理由を look の答えに書きます。
- `--mcp` の tap、swipe、type、paste は、その look を始めてからページがデバイスを操作していれば断ります（look し直すよう答えます）。look の画像の 0.5 秒前までの操作も同じです。ページの操作が動いている間の tap などは、それが終わるのを待ってから断ります。エージェントが tap や swipe をした位置は、ページに輪で出します。デバイスへの接続が切れたときは、つなぎ直しません（2 本目のストリームになるためです）。エージェントとページに、view を起動し直すよう伝えます。
- iPhone Duo で、Chrome のページで見ながら `--mcp` の look を測りました。USB で 0.4〜1.1 秒、自宅の Wi‑Fi で 0.5〜1.3 秒でした。続けて呼ぶと、キーフレームと同じく約 1.05 秒おきになります。その間、ページの画像は止まりませんでした。別の接続（RoamRun のアプリ）から look したときは、ページの画像が約 9 秒止まりました。デバイスが画面のストリームを 1 本ずつしか送らないためです。最初は JSON-RPC を送るスクリプトで試しました。2026-11-06 には、Codex app-server 0.156.1 の MCP クライアントでも HTTPS 経由で接続しました。ツール一覧の取得、look、tap、swipe が成功し、T3 Code のブラウザに操作位置の輪が出ました。この確認では Codex が `mcpServer/tool/call` を呼び、別のモデルのターンは実行していません。Claude Code なら、次のように加えます。`claude mcp add --transport http <名前> http://<アドレス>:<ポート>/mcp --header "Authorization: Bearer <トークン>"`
- 動いている間、デバイスはこのコマンドだけのものです。ほかのコマンドからは使わないでください。画面のストリームは、ページが見ている間だけ動きます。ページには、届いた順にアクセスユニットを送ります。パラメータセットの付いたキーフレームより前のものは送りません。パラメータセットなしで届いたキーフレーム（IDR が続いたとき）には、最後に見たものを補います。ページは、フレームを復号してから受け取りを知らせます。ページごとに、まだ表示されていないいちばん古いフレームを見ます。送る順番を待つものと、送ったのにページから受け取りの知らせがないものです。それが古すぎたら、そのページは次のキーフレームまで飛ばし、キーフレームを求めます。古すぎるとは、そのページのいちばん短い往復の時間より 0.5 秒以上古いことです。最初の受け取りの知らせが来るまでは、往復を 1.5 秒とみなします。デバイスが答えるのは 1.05 秒に 1 回までです。最後のページがなくなると、look のあとと同じく、5 秒ほどでストリームが止まります。画面が止まって映像が来ていない間でも同じです。Ctrl-C でも止まります。
- 何も変わらない画像（1 枚が数百バイト）だけが 1 秒続くと、どの画面が点いているかをデバイスに尋ねます。続く間は 2 秒ごとに尋ねます。送っている画面と違えば（iPhone Duo を閉じたときや開いたとき）、ストリームを止め、点いている画面で始め直します。Duo では、閉じてからページに外側の画面が出るまで約 3 秒でした。Duo の内側の画面は、閉じたあとも約 9 秒、変わらない画像を送り続けます。画面が止まっていると、デバイスは報告（RTCP）を送り続けたまま映像を自分で止め、あとで送り直します。USB でつないだ Duo では、5 分のうち最長 9.7 秒止まりました。その間ストリームはそのまま保ちます。始め直すのは、映像も報告も 8 秒来ないときと、止まっている間に求めたキーフレーム（新しいページや look のため）が届かないときです。
- デバイスには、フレームごとの受け取りの知らせと、50 ミリ秒ごとの受信の報告を返します。形は idevice の `build_frame_ack` と `build_rctl` の説明どおりです。比べるために `ROAMRUNCTL_VIEW_FEEDBACK=off` とすると、どちらも送りません。
- ページでの操作は次のとおりです。クリックはタップ、ドラッグはスワイプ（50〜5000 ミリ秒）になります。動かさずに 0.5 秒以上押したままにすると長押しになります（押していた時間だけ、動かないスワイプを送ります）。2 本の指ではピンチになります。指の間隔の変わり方と回った角度を、指を置いた位置の中ほどで送ります。送るのは、1 本目の指を離したときです。3 本以上では何も送りません。キーは入力として送ります。送れるのは US キーボードで打てる文字と Return、Backspace で、それ以外のキーは送れないとページに出します。US キーボードにない文字のキーを続けて押すと、まとめて 1 回の `paste` で送ります。キーボードのフォーカスがボタンにあるとき、Enter と Space は送らずに、そのボタンを押します。ボタンで、ホーム、ロック、音量を押せます。Type を押すと、スマホでは画面のキーボードが出て、打った文字を送ります（パソコンでは、そのマシンの入力メソッドで打てます）。US キーボードで打てる文字は 1 キーずつ送ります。打てない文字（日本語など）は、変換を確定したあとに `paste` で送ります。これは数秒かかり、デバイスのクリップボードにその文字が残ります。Refresh はキーフレームを求めます。Full screen は、ブラウザの全画面にします。ページに全画面を許さないブラウザ（iPhone の Safari）では、ウィンドウいっぱいに広げます。操作は 1 つずつデバイスに送ります。1 つのページから順番を待てるのは 20 個までで、それを超えた分は断ります。なくなったページの操作は送りません。それぞれの結果はページに返し、失敗したものは画像の上に出します。ページからの長押しとピンチは、デバイスではまだ試していません。
- 音。デバイスは音を AAC-ELD で送ってきます。Chrome も Safari も、これを復号できません（Mac と iPhone で `AudioDecoder` に尋ねました）。このマシンが Mac なら、ここで AudioToolbox を使って復号します。それを、Sound ボタンを押したページに PCM で送ります（48 kHz、2 チャンネル、16 ビットで、約 190 KB/秒）。ページは、音専用の WebSocket で届いた順に鳴らします。先読みは 0.15〜0.5 秒です。途切れるたびに 50 ミリ秒伸ばし、10 秒途切れなければ 25 ミリ秒縮めます。それより先の分は捨てます。iPhone の Safari に Tailscale を通して送ったとき、映像と同じ WebSocket では、音がフレームの後ろで最大 2 秒止まりました。音専用の WebSocket にすると、ほとんど途切れなくなりました。Linux と Windows では音は出ず、ページの Sound ボタンにもそう出します（音が出るかどうかは、サーバーの `hello` で伝えます）。iPhone Duo を USB でつなぎ、Mac の Chrome と iPhone の Safari で聞きました。画像とのずれは測っていません。
- ページがデバイスを映せないときは、待ち続けずに、理由を画像の上に出します。対象は次の場合です。`VideoDecoder` のないブラウザ、安全なページでないとき（代わりに開くアドレスも出します）、デコーダーが HEVC を受け付けないブラウザです。最後のものは、デコーダーがそう答えたときと、その接続で画像が出る前に 10 秒のうちに 3 回失敗したときです。トークンが断られたときと、デバイスへの接続が切れたとき（view を起動し直します）も出します。つながってからサーバーから 5 秒何も届かないとき（サーバーは 1 秒ごとに数を送ります）と、15 秒たってもつながらないときは、つなぎ直します。
- 上の帯には、画像が出ているかどうかと、1 秒あたりのフレーム数と KB を出します。Details には、1 秒ごとに受け取ったバイト数とフレーム数、復号にかかった時間、求めたキーフレームと届いたキーフレームの数、飛ばした回数を出します。クリックから変化までの時間も出します。クリックしてから、その周りの 48 × 48 ピクセルが変わった最初の復号画像までの時間です。ほかに、大きさを 3 つ出します。サーバーがストリームの SPS から読んだもの、切り取ったもの、ブラウザで復号されたものです。ストリームの画像は、右と下に余白を持つことがあるので、それを切り取ります。
- 接続ごとに 1 行を、`mcp --http` と同じ形で標準エラー出力に記録します。トークン、入力した文字、画像は記録しません。
- WebSocket のメッセージの形は次のとおりです。サーバーからのバイナリのメッセージは、1 バイト（1 ならキーフレーム）、サーバーの時刻（ミリ秒、8 バイトのビッグエンディアン）、アクセスユニット（Annex B）の順に並びます。テキストのメッセージは JSON です。`hello`（`feedback`、`sound`：true か、音が出ない理由）と `picture`（`codec`、`width`、`height`、`crop`）があります。ほかに `counts`、`status`、`agent`（`what`、`points`）、`done`、`error` があります。音もバイナリのメッセージで、1 バイト（2）、時刻、PCM（リトルエンディアン）の順に並びます。ページからのメッセージも JSON で、`hello`（`token`）、`ack`（`t`）、`keyframe` があります。音のためには、ページが 2 本目の WebSocket を開きます。その `hello` には `only: "sound"` を付けます。この接続は音だけを運ぶので、フレームの後ろで音が待たされることはありません。操作には `tap`（`x`、`y`、0〜1）、`swipe`（`x1`、`y1`、`x2`、`y2`、`ms`）、`pinch` を使います。`pinch` は `x`、`y`、`scale`（0.25〜4）、`degrees`（−180〜180）、`ms` を持ちます。ほかに `type`（`text`）、`paste`（`text`）、`press`（`button`）があります。

## HTTP プロキシを通す（`ROAMRUNCTL_PROXY`）

HTTP プロキシを通してしか tailnet に届かないマシンでは、`ROAMRUNCTL_PROXY=http://<ホスト>:<ポート>` を指定します。すると roamrunctl は、そのプロキシの `CONNECT` を通してつなぎます。対象はデバイスへの接続（応答するかの確認、ペアリング用ポート、トンネル用ポート）で、`look`、`install`、`launch`、`mcp` なども含みます。relay への接続（`--relay`）も対象です。

- 受け付けるのは `http://<ホスト>:<ポート>` だけです。ユーザー名とパスワード、パス、`https://`、SOCKS は受け付けません。`<ホスト>` は名前か IPv4 アドレスです（角かっこで囲んだ IPv6 アドレスは受け付けません）。名前なら、名前から得たアドレスを順に試します。それ以外の値なら、何もする前に止まります。空の値なら、指定なしとみなします。`HTTPS_PROXY`、`http_proxy`、`ALL_PROXY` などは読みません。
- `CONNECT` へのプロキシの答えは、直接つなぐときと同じ時間だけ待ちます。
- デバイスとのペアリング（デバイスの Wi‑Fi で行う `pair control` のやり取りと、`pair introduce`）と、デバイスに署名するマシン（B）への接続は、プロキシを通しません。ただし、ペアリングを保存する前の、tailnet 越しの試しの接続（`pair control`）は、プロキシを通します。
- userspace で動く Tailscale は、tailnet へのこうしたプロキシを出せます。次のように動かします。

  ```sh
  tailscaled --tun=userspace-networking --outbound-http-proxy-listen=127.0.0.1:1056
  export ROAMRUNCTL_PROXY=http://127.0.0.1:1056
  ```
- この変更のビルドで、2026-10-24 に Xcode Cloud から iPhone 15 Pro に対して試しました。`install --relay … --launch` が通りました。relay を使わない `key import -`、`install --launch`、`look` も通りました。手順は [docs/xcode-cloud.ja.md](xcode-cloud.ja.md) にあります。Mac からは、`CONNECT` を記録する試験用のプロキシを通して、`look`、`install --launch`、`install --relay … --launch` を試しました。

## アプリのインストール

- `install` には、対象のデバイス向けにビルドした `.ipa` か、署名済みの `.app` ディレクトリを指定します。`roamrunctl` はコンパイルも署名もしません。
- `.ipa` は、何かを送る前に検査します。`roamrunctl install`（デバイスを開く前）でも MCP でも同じです。`Payload` の中は 1 つの `<名前>.app` だけで、`.DS_Store` のような隠しファイルのほかには何も入っていないこと。`.bundle` は断ります。`.app` で終わる名前は、隠しファイルでもアプリとして数えます。アーカイブの申告で、展開後の大きさが 4 GiB 以下であること。アプリの bundle identifier は、インストールと同じ方法で見つけます。名前が `/` で 3 つに区切られ、`Info.plist` で終わるファイルを、アーカイブの順に読みます。最初に bundle identifier が書かれていたファイルが `Payload/<名前>.app/Info.plist` であること。それより前にある identifier のないファイル（アプリの中にある Firebase の `GoogleService-Info.plist` など）は使わずに次を読みます。読むファイルはどれも 1 MiB 以下の plist であること。`.app` ディレクトリは検査しません。
- `.ipa` は、送る前にまるごとメモリへ読み込みます。`--max-upload` の上限いっぱいのアップロードなら、インストールの間、このマシンで同じだけのメモリを使います。
- `.app` ディレクトリは、デバイス上にその名前のまま一時的に置かれます。`.ipa` は、決まった 1 つの名前で置かれます。**1 台のデバイスに、別々のコマンドから同時にインストールしないでください。** コマンドどうしで調整する仕組みはありません。1 つの `mcp` サーバーの中では、あるデバイスのインストール中に、そのデバイスへの 2 つ目のインストールは断ります。
- インストールの前に、そのアプリの起動中のプロセスを終了させます。アプリは、bundle identifier（`.ipa` の中のもの、`.app` フォルダなら Info.plist のもの）で見分けます。iOS も自分で終了させます。ただ iOS 27.0 は、ワイヤレス充電器の上のデバイスで前面にあるアプリを終了させず（ケーブルでの充電は試していません）、それが前面から外れるまでインストールを待たせました。122 秒かかったことがあり、315 秒でタイムアウトしたこともあります。プロセスを見つけられないときや終了させられないときは、これまでどおりインストールします。終了は強制（SIGKILL）で、アプリ拡張も含み、アップロードを始める前に行います。そのためアプリは状態を保存できず、アップロードの間も動いていません。インストールが失敗しても、終了したままになります。0.8.1 にはなかった動きです。
- 中断されたインストールの残りは、次に `.app` をインストールするときに、可能な範囲で片づけます。コマンドは、転送するサイズと上限の時間を表示してから、結果を報告します。
- `install --launch` は、インストールに続いて、同じデバイスへの接続のまま、アプリを起動します。bundle identifier は `.ipa` の中から、`.app` フォルダならその `Info.plist` から読みます。`Info.plist` に bundle identifier がなければ、何もインストールしません。起動を試す前に、インストールできたことを表示します。
- MCP の `install` は、インストールを始めた時点で答えます。答えには、bundle identifier（`.app` ならそのパス）、大きさ、インストールの id（`(install 3f2a9c0e1b7d4a65)`。乱数）、上限の時間が入ります。進み具合は `install_status` が、そのデバイスの最新のインストールについて答えます。続いているならその経過時間、終わったなら成功か、失敗の理由です。`"install": "<id>"` を渡すと、そのインストールについてだけ答えます。そのあとにデバイスで別のインストールが始まっていても、終わったインストールは、デバイスごとに直近の 16 件まで、どう終わったかを答えます。それより前のものや、サーバーが起動し直す前のものは、どう終わったか分からないというエラーになります。そのため、別の呼び出し元が同じアプリを入れても、自分のインストールと取り違えません。終わるまでは、そのデバイスへのほかの呼び出しには、すべて「インストール中」と答えます。そのデバイスの最新の `look` も使えなくなります。標準入出力では、標準入力が閉じたときに続いているインストールは、最後まで終えてからサーバーを終えます。HTTP では、Ctrl-C で止めると、インストールもそこで止まります。

## `pair introduce` のオプションと結果

```text
roamrunctl pair introduce --host <host> --to <device> [--offer <line>] [--as <name>] [--deadline <secs>] [--on <address>]
```

- ホストでは、次のいずれかを実行しておきます。
  - `roamrunctl pair control --with <仲介マシン>`
  - `roamrun pair control --with <仲介マシン>`（RoamRun のアプリを起動しておく）
  - `roamrun pair xcode --with <仲介マシン>`（Xcode の Device Hub で待機しておく）
- どちらの側のコマンドを先に実行しても構いません。
- RoamRun を入れた Mac を、仲介マシンとして使うこともできます。その場合は `roamrun pair introduce --host <ホスト> --to <RoamRun に保存してあるデバイスの名前>` を実行します。ただし、仲介マシンが Mac で、ホストが `roamrunctl` の構成は、この文書を書いた時点では試していません。
- `--offer` は、Xcode のオファーを TCP 41830 で要求する代わりに、手で渡すためのオプションです。`--offer "$(ssh <離れた Mac> roamrun pair xcode)"` のように使います。ホストのポート 41830 が閉じている場合のためのものです。デバイス操作のペアリングには、これにあたるオプションはありません。
- `--as` は、ホストがデバイスを保存するときの名前を指定します。ホストは、その名前を拒否することがあります。Xcode のペアリングでは、その場合、表示されたデバイスの情報を `roamrun devices add <行> --as <別の名前>` で手動で追加できます。ホストが `roamrunctl` の場合は、ホスト側の `--as` が優先されます。
- `--on` は、仲介マシンがデバイスのネットワークに複数のアドレスを持つときに、使うローカルの IPv4 アドレスを指定します。指定しなければ、システムがデバイス宛ての通信に使うアドレスを選び、ほかの候補を表示します。
- Xcode の場合、ペアリングのコードはホストの Device Hub に表示されます。仲介マシンが作るものではありません。デバイス操作の場合は、関係するターミナルに表示されます。
- Apple Vision Pro は、Remote Devices（デバイスの 設定 > 一般 > Remote Devices）を開くと、Mac に選ばれるのを待つ状態になります。Apple TV も、`設定 > リモコンとデバイス > リモコンアプリとデバイス` を開けば、同じ状態になります。このペアリングは RoamRun を入れた Mac どうしで行うもので、どちらのデバイスでもその形で動作を確かめてあります。こうしたデバイスに対して、Mac の `roamrun pair introduce` は、Mac 以外を `--host` に指定すると拒否します。どちらのデバイスも、`roamrunctl` と組み合わせた動作は確認していません。
- Xcode の場合、デバイスの情報が取得できれば、`roamrun devices add` に渡せる形で 1 行、**標準出力**に書かれます。状況や診断のメッセージは、**標準エラー**に出ます。

| 終了コード | 意味 |
|---|---|
| 0 | ホストが、ペアリングを保存したと報告した。`--offer` の場合は、Xcode のペアリングを試み、デバイスの情報を表示した。ホストには知らせていないので、表示された情報を、ホストで `roamrun devices add` を使って追加する必要がある |
| 1（デバイスの情報の行あり） | Xcode のペアリングを試みたが、ホストが保存を確認しなかった。ホストで手動で追加する |
| 1（デバイスの情報の行なし） | ペアリングが完了しなかった、デバイスが公開するサービスが見つからなかった、またはデバイス操作のペアリングが保存されなかった。標準エラーを確認する |
| 2 | コマンドラインの指定の誤り。サポートしていない `--mac` など（`--offer` なしで `--deadline` に 300 を超える値を指定した場合は 1） |

Ctrl-C を押したとき、ターミナルを閉じたとき、SSH のセッションが切れたときは、終了する前に Bonjour での公開をやめようとします。この動作は macOS で確認しています。Windows で確認したのは、Ctrl-C と、コンソールを閉じた場合です。

## うまくいかないとき

- **`roamrunctl` が見つからない：** Linux では、`~/.local/bin/roamrunctl` と指定して実行するか、`PATH` を直します。Windows では、展開したディレクトリの中の実行ファイルを指定するか、そのディレクトリを `PATH` に追加します。
- **Tailscale 上の名前が見つからない：** コマンドを実行するマシンで `tailscale status` を実行してください。iPhone に付けた表示名ではなく、Tailscale の DNS 名を使います。関係するマシンとデバイスがすべて、意図した tailnet でオンラインになっていることも確認してください。
- **`pair control --to` を実行しても、デバイスに表示されない：** 次の点を確認してください。
  - デベロッパモードが有効で、Wi-Fi に接続しているか
  - Tailscale が、ローカルの IPv4 で直接つながっているか
  - mDNS が通るか
  - ファイアウォールが、外からの接続を許可しているか

  コマンドの出力に、ポートと、通す必要のあるデバイスのアドレスが表示されます。
- **`pair control --with` が、コードが出る前に失敗する：** 仲介マシンから、操作マシンの TCP 41830 と、動的なペアリング用ポートに届く必要があります。`pair introduce` の出力に「デバイス自身の公開するサービスが見えない」と出る場合、そのデバイスはまだ一度もペアリングされていない可能性があります。先にデバイスと同じ Wi-Fi にあるマシンでペアリングしてください。
- **コードが拒否された：** 完了しなかったペアリングは保存されません。仲介をやり直し、新しく表示されたコードで試してください。離れた場所で待っているコマンドは、次の試行のために動き続けていることがあります。その場合は、出力にそう表示されます。
- **B で `roamrunctl devices` に何も表示されない：** 署名マシンで `roamrunctl sign phone --for <操作マシン>` を起動してください。TCP 41831 への接続の許可も必要です。どちらかのマシンにタグが付いているか、別の Tailscale ユーザーのものである場合は、操作マシンで `ROAMRUNCTL_SIGNER` を設定します。
- **MCP から、暗号化したデバイスを開けない：** `mcp` はターミナルで入力を求められません。MCP サーバーの環境変数に、`ROAMRUNCTL_PASSPHRASE_FILE` か `ROAMRUNCTL_PASSPHRASE_COMMAND` を設定してください。スキルを入れただけでは、MCP サーバーは起動しません。
- **それまで使えていたペアリングで接続できなくなった：** 同じマシンからデバイスをペアリングし直すと、デバイス上の以前のペアリングは置き換えられ、古いペアリング情報は拒否されるようになります。`roamrunctl devices remove <名前>` で古い情報を削除して、ペアリングし直してください。

## ビルドと確認

リポジトリを取得した状態で、`Rust/roamrunctl` で実行します。

```sh
cargo build --locked
cargo test
# macOS で。この Mac の LAN のアドレスを渡す
python3 scripts/local-check.py target/debug/roamrunctl "$(ipconfig getifaddr en0)"
```

この確認では、実際のデバイスとはペアリングしません。オファーは、試験専用の Bonjour サービス（`_rrtest._tcp`）で公開します。偽のデバイスは、実行中だけ、本物と同じ `_remotepairing._tcp` で LAN 上に公開されます。確認するのは、サービスの発見、想定外の相手の拒否、TCP の中継、デバイスの情報の作成、公開の後始末です。続けて、デバイス操作について、偽のホストとのやり取り、オファーの公開、中継、コードの表示、終了コード 0 を確認します。この Mac のポート 41830 と 53050 が空いている必要があります。

Mac 側の関連する実装は、`Sources/RoamRun/Pairing/` にあります。ファイルは、`IntroductionLines.swift`、`Introductions.swift`、`PairByName.swift`、`ControlIntroductions.swift` です。
