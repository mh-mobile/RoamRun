# roamrunctl リファレンス

<p align="center"><a href="roamrunctl-reference.md">English</a> | 日本語</p>

[roamrunctl の README](../Rust/roamrunctl/README.ja.md) を補う、細かい動作と制約の一覧です。鍵の置き場所の 2 つの構成、離れた場所からのペアリング、署名の依頼については README に図があります。この文書では、前提条件、ネットワーク上の制約、例外的な動作を説明します。

マシンの呼び方は README と同じです。

| 呼び方 | 役割 |
|---|---|
| 操作マシン | `look`、`install`、`launch`、`mcp` を実行するマシン |
| 仲介マシン | デバイスと同じ Wi-Fi にあり、離れた場所のマシンのペアリングを仲介するマシン |
| 署名マシン | B で秘密鍵を持ち、接続のたびに署名するマシン。A では操作マシン自身が鍵を持ちます |
| ホスト | `pair introduce --host` で指定する、デバイスとペアリングし、その鍵を保存する側のマシン |

1 台が複数の役割を兼ねることもあります。仲介マシンはペアリングの最初の接続を中継するだけで、ホストの秘密鍵は持ちません。B でも、デバイスの操作は操作マシンとデバイスの間で直接行われ、署名マシンは経由しません。

## インストール

- リリースのアーカイブは、次の 4 つです。
  - `roamrunctl-linux-x86_64.tar.gz`
  - `roamrunctl-linux-aarch64.tar.gz`
  - `roamrunctl-windows-x86_64.zip`
  - `roamrunctl-windows-aarch64.zip`
- どのアーカイブにも、バイナリ、README、`SKILL.md`、ライセンス表記が入っています。チェックサムは `roamrunctl-SHA256SUMS` にあります。
- Linux 版のバイナリは静的リンクです。`~/.local/bin` に入れたあと `roamrunctl` が見つからない場合は、そのディレクトリを `PATH` に追加するか、`~/.local/bin/roamrunctl` と指定して実行します。
- Windows 版のアーカイブは、サブディレクトリに展開されます。`.\roamrunctl-windows-x86_64\roamrunctl.exe` のように指定して実行するか、そのディレクトリを `PATH` に追加します。バイナリにコード署名はありません。Windows 11 では、初めて Bonjour で公開したときに、Windows ファイアウォールが通信を許可するか尋ねてきたことがあります。このときは、プライベートとパブリックの両方で許可しました。管理者として実行した PowerShell では、何も尋ねられませんでした。
- `cargo install --locked --git ...` には、Rust 1.89 以降と C コンパイラが必要です。これはソースからのビルドで、リリースに含まれる静的リンクの Linux 版とは別のものです。`roamrunctl` は crates.io には公開していません。Homebrew の formula は Homebrew 本体ではなく、`mh-mobile/tap` にあります。
- 表示されるバージョンは RoamRun のバージョンです。同じペアリングに関わるマシンでは、バージョンをそろえてください。0.7.0 より前の `pair introduce` は、`--host` ではなく `--mac` を使っていました。古いリリースが案内するコマンドには、`--mac` と書かれています。

## 最初のペアリングとネットワークの前提

- iPhone / iPad は、Tailscale を入れてデベロッパモードを有効にし、Wi-Fi に接続して、起動後に一度ロックを解除しておきます。モバイル通信でしか届かないデバイスは、新しい接続を受け付けません。
- `pair control --to` は、デバイスと同じ Wi-Fi にあるマシンでペアリングするコマンドです。そのネットワーク上で、Tailscale がデバイスに IPv4 で直接つながっている必要があります。リレー経由や IPv6 では動きません。
- 離れた場所から `pair control --with <仲介マシン>` でペアリングする場合は、次の前提条件があります。仲介マシンはまず、デバイス自身が公開している `_remotepairing._tcp` のサービスを見つける必要があります。デバイスがこのサービスを公開するのは、一度ペアリングしたあとです。一度もペアリングしていないデバイスは、先にデバイスと同じ Wi-Fi にあるマシンでペアリングしてから（Mac の Xcode など）、もう一度仲介を試してください。コマンドの出力では、この最初のペアリングの方法として、仲介マシンでの `roamrunctl pair control --to <デバイス>` も案内されます。ただし、Mac を使わないこの手順は試していません。
- iOS の Introducer アプリを使うと、デバイス自身が仲介役になります。操作マシンで `roamrunctl pair control --with <デバイスの Tailscale 上の名前>` を実行し、アプリに操作マシンの名前を入力します。この場合、仲介マシンは要りません。
- `--to`、`--with`、`--host`、`--for` には、iOS の「設定」に出るデバイス名ではなく、Tailscale 上の名前（`tailscale status` に表示されるもの）を指定します。同じ tailnet のマシンの短い名前か、Tailscale の DNS 名全体で指定できます。複数のマシンに当てはまる名前は拒否されます。

## ポートとファイアウォール

以下に出てくる「オファー」は、ペアリングを始めるためにホストが出すデータです（`--offer` で渡すものと同じです）。

| 操作 | 接続の向き | TCP ポート |
|---|---|---|
| `pair control --to` | デバイス → 操作マシン（Wi-Fi 上） | コマンドが表示する動的なポート |
| `pair control --with` | 仲介マシン → 操作マシン（Tailscale 経由） | 41830。続いて、ペアリング中に表示される別の動的なポート |
| `pair introduce` | デバイス → 仲介マシン（Wi-Fi 上） | 仲介マシンが表示する動的なポート |
| `pair introduce` | 仲介マシン → ホスト（Tailscale 経由） | オファーを要求するときは 41830。続いて、ホストのペアリング用ポート |
| `look`、`install`、`launch`、`mcp` | 操作マシン → デバイス（Tailscale 経由） | デバイスのペアリング用ポート。続いて、その接続のためにデバイスが指定するトンネル用のポート |
| B（`sign --for`） | 操作マシン → 署名マシン（Tailscale 経由） | 41831 |

- `pair control --to` では、デバイスは Wi-Fi 上の自分のアドレスから、コマンドが表示した 1 つの TCP ポートに接続してきます。コマンドはアドレスを 2 つ表示します。このマシンのアドレスと、デバイスのアドレスです。デバイスのほうには「has to be let in」（通す必要がある）と添えてあります。操作マシンのファイアウォールで、この接続を許可してください。Wi-Fi 上で Bonjour / mDNS（UDP 5353）が通ることも条件です。
- ファイアウォールを有効にして実際に試したのは、次の 1 通りです。ufw を有効にした Ubuntu で、試験用のサービスを使った `pair introduce` を、デバイスの代わりに Mac を相手にして実行しました。mDNS は ufw の初期設定のままで通りました。TCP 接続は、`sudo ufw allow proto tcp from <デバイスのアドレス>` を実行するまで応答がなく、実行すると接続できました。表示されたポートだけに絞ったルールは試していません。firewalld など、ほかのツールも試していません。
- `pair control --with` では、指定した仲介マシンから、操作マシンの TCP 41830 と、その回に表示される新しいポートへ接続できるようにします。Tailscale のアクセス制御と、操作マシンのファイアウォールの両方で許可が必要です。動的なポートは、試すたびに変わります。41830 が閉じていると、仲介マシンからは「ホストが待っていない」ように見えます。ペアリング用のポートが閉じている場合は、別のメッセージで知らされます。
- `pair introduce` では、デバイスが仲介マシンの表示したローカルの TCP ポートに接続できることも必要です。`--offer` で Xcode のオファーを渡した場合、ホストの 41830 への問い合わせは行いません。その場合も、ホストのペアリング用ポートには届く必要があります。
- B では、署名マシンが、指定した操作マシンからの TCP 41831 への接続を受け付けるようにします。署名マシンがスクリーンショットや入力を中継することはありません。デバイスとの通信は、操作マシンとデバイスの間で直接行われます。
- macOS では、ファイアウォールを有効にしているとき、`roamrunctl` が外からの接続を受け付けてよいか尋ねられました（Linux のマシンをデバイスの代わりにして、1 回確認）。
- roamrunctl は、Wi-Fi 上の自分のアドレスを、ネットワークインターフェイスのアドレスから選びます。経路表は、そのネットワークに複数のインターフェイスがあるときに、どれを使うかを決めるためだけに使います。ある Windows のマシンでは、「Use Tailscale subnets」の設定によって自分の LAN への経路が Tailscale 経由になっていましたが、ペアリングは問題なく通りました。
- `sign` と `pair control --with` は、このマシンの Tailscale のアドレスで待ち受けます。Tailscale をユーザースペースネットワーキングだけで動かしている環境では、どちらも試していません。

## 時間制限

- `pair control --to`：全体で 7 分です。コードが表示されてから入力するまでは 3 分です。コードを間違えるか、時間切れになると、コマンドは終了します。もう一度実行してください。
- `pair control --with`：仲介マシンからの接続を最大 10 分待ちます。仲介マシンが `roamrunctl` の場合、仲介マシンはペアリングを 5 分待ちます（このマシンは最大 7 分待ちます）。コードが表示されてから入力するまでは 3 分です。デバイスから接続があったものの、ペアリングが成立しなかった場合に限り、このマシンは次の接続を待ち受けます。試行は最大 5 回です。そのたびに、仲介をやり直す必要があります。仲介マシンが時間切れになると、このコマンドは終了します。
- `pair introduce`：Wi-Fi 上への公開は、既定で 5 分です（`--deadline`）。ホストにオファーを要求する場合、`--deadline` に指定できるのは 300 秒までです。その前に、ホストの TCP 41830 を最大 10 分待つことがあります。どちらのマシンのコマンドを先に実行しても構いません。
- `install`：5 分に、1 MB あたり 15 秒を加えた時間が上限です。コマンドは、サイズと上限の時間を表示したあと、終わるまで何も表示しません。デバイスと同じ Wi-Fi で試したとき、3 MB で約 25 秒、37 MB で約 2 分半かかりました。

## ペアリング情報とパスフレーズ

- ファイルは、Linux と macOS では `~/.config/roamrunctl/devices` に保存されます。`XDG_CONFIG_HOME` が絶対パスで設定されていれば、`$XDG_CONFIG_HOME/roamrunctl/devices` です。Windows では `%LOCALAPPDATA%\roamrunctl\devices` です（なければ `%APPDATA%`）。デバイスごとに `<名前>.json` が作られ、暗号化した場合は `<名前>.age` になります。
- Linux と macOS では、ディレクトリはモード 0700、ファイルは 0600 で作られます。グループやその他のユーザーに何らかの権限が付いているファイルは、読み込みを拒否します。Windows では、プロファイルのディレクトリの権限に任せていて、同じ確認は行いません。
- 暗号化していない JSON のペアリング情報は、認証情報そのものです。これを読めて、**かつ**デバイスに通信が届くプログラムは、デバイスを使えます。`pair control` と `key import` に `--passphrase` を付けると、ファイルを age のパスフレーズ形式で暗号化します。パスフレーズをコマンドの引数として渡すことはできません。
- パスフレーズは、次の順で、最初に設定されている環境変数から取得します。
  1. `ROAMRUNCTL_PASSPHRASE_FILE`
  2. `ROAMRUNCTL_PASSPHRASE_COMMAND`
  3. `ROAMRUNCTL_PASSPHRASE`
- 設定されている環境変数からの取得に失敗すると、次は試さずに止まります。`ROAMRUNCTL_PASSPHRASE_COMMAND` に指定したコマンドは `sh -c` で実行されます（Windows では `cmd /S /C`）。`ROAMRUNCTL_PASSPHRASE` に入れたパスフレーズは、そのシェルから起動したすべてのプロセスの環境変数に入ります。どれも設定されていなければ、対話的に実行するコマンドは入力を求めます。

| コマンド | パスフレーズの扱い |
|---|---|
| `pair control --passphrase`、`key import --passphrase` | 暗号化したペアリング情報を新しく作るときに、2 回入力を求める。環境変数が設定されていれば、そこから取得する |
| `look`、`install`、`launch` | 暗号化したペアリング情報を開くときに入力を求める。環境変数が設定されていれば、そこから取得する |
| `mcp` | 入力を求められない。暗号化したペアリング情報を開くたびに、環境変数からの取得が必要 |
| `sign` | 起動時に、暗号化したペアリング情報ごとに、取得するか入力を求める |
| `devices`、`devices remove` | パスフレーズは不要 |

- MCP クライアントで使う場合は、README にある登録の設定に加えて、MCP サーバーの環境変数に、上の 3 つのいずれかを設定します。
- macOS で、**対応する項目がすでにキーチェーンにある場合**は、`ROAMRUNCTL_PASSPHRASE_COMMAND` に次のコマンドを指定できます。

  ```sh
  security find-generic-password -a "$USER" -s roamrunctl -w
  ```
- 同じマシンからデバイスをペアリングし直すと、デバイス上の以前のペアリングは置き換えられます。古いペアリング情報では接続できなくなるので、`roamrunctl devices remove <名前>` で削除してください。ペアリングを取り消す場合は、デバイスのデベロッパモードの一覧からも、そのマシンを削除します。
- 接続では、保存してあるポートを最初に試し、続いて 49152〜49167 の残りを試します。デバイスを 2 回再起動し、ネットワークから外して戻したときには、デバイスは毎回 49152 を公開していました。どのポートでも届かない場合は、ペアリングし直してください。
- RoamRun を入れた Mac で鍵を作って、取り込むこともできます。Mac で `roamrun key create <デバイス> device.key` を実行し、操作マシンで `roamrunctl key import device.key` を実行します。取り込みでは、Tailscale 経由でデバイスへの接続を確かめてから情報を保存し、成功すると取り込み元のファイルを削除します。

## B：署名と信頼関係

B では、署名マシンが秘密鍵を持ちます。操作マシンは、デバイスへ新しく接続するたびに、必要な署名だけを依頼します。

- `roamrunctl sign <デバイス> --for <マシン>` は、指定した Tailscale 上の 1 台にだけ応答します。相手は、tailnet の IP アドレスと、Tailscale のノード ID で確認します。既存のペアリング情報を使った接続検証に必要な形式の依頼にだけ、署名します。新しいペアリングを作るための依頼には署名しません。依頼は 1 つずつ処理します。
- `sign` は、起動時に、指定したデバイスのペアリング情報を読み込みます。実行中に削除されたり、置き換えられたりした情報には、それ以降署名しません。新しい情報で署名するには、`sign` を再起動します。
- 既定では、操作マシンは**オンラインで、タグがなく、同じ Tailscale ユーザーのもの**であるマシンから署名マシンを探します。操作マシン自身にタグが付いていないことも条件です。この方法は、信頼できる tailnet では手軽です。ただ、ほかの人の動かすマシンが混ざる環境では、これに頼らないでください。
- 次のいずれかにあたる場合は、**デバイスを初めて使う前に** `ROAMRUNCTL_SIGNER=<署名マシンの Tailscale 上の名前>` を設定してください。
  - どちらかのマシンにタグが付いている場合
  - 2 台が別のユーザーのものである場合
  - 別のマシンも同じデバイス名で `sign` を実行できる場合

  Linux / macOS での例です。

  ```sh
  export ROAMRUNCTL_SIGNER=home-pc
  roamrunctl devices
  roamrunctl look phone
  ```

  PowerShell では `$env:ROAMRUNCTL_SIGNER = 'home-pc'` です。エージェントから使う場合は、MCP サーバーの環境変数に設定します。
- B の構成でデバイスを初めて使うとき、`roamrunctl` は、どの署名マシンがどのデバイスを担当するか（以下、署名マシンとの対応）を保存します。**秘密鍵は保存しません。** 以後は、この対応でしか使いません。署名マシンを指定していない場合は、同じユーザーのマシンのうち、その名前のデバイスに署名できると応答したマシンを信用します。2 台が応答した場合は、Tailscale 上の名前が辞書順で先のほうを選びます。信頼できないマシンが混ざる環境では、自動で探す方法に頼らないでください。対応を保存できない場合、そのデバイスは使いません。
- **操作マシン**で `roamrunctl devices remove <名前>` を実行すると、保存した対応が消えます。署名マシンにある秘密鍵は**消えません**。同じ 1 台のデバイスに対して 2 台の署名マシンが別々のペアリングを持つ場合は、それぞれ別の名前で保存しておく必要があります。
- 署名の仕組みでは、秘密鍵が操作マシンに送られることはありません。ただし、**これでできる操作が制限されるわけではありません。** `sign` が応答している間、許可された操作マシン上のどのプログラムでも、デバイスへの接続を開けます。接続したセッションでは、画面の確認、入力の送信、アプリのインストールができます。`sign` を止めると**新しい**接続には署名されなくなりますが、すでにある接続（開いたままの MCP の接続など）は切れません。`sign` は、署名した接続を 1 つずつログに出します。タップやスクリーンショット、インストールのたびに承認を求めるものではありません。
- 接続済みの操作マシンから、デバイスに新しいペアリングを追加できるかどうかは、**試していません**。そのため、B なら操作マシン上のソフトウェアが恒久的なアクセスを得ることはない、とは言えません。

## MCP のツール

- `roamrunctl mcp` は、標準入出力で通信します。MCP の `look` は JPEG の画像をエージェントに返し、単体の `roamrunctl look` コマンドは PNG を保存します。どちらも、画像の長辺は最大 1280 ピクセルです。
- MCP の `look` 1 回につき、60 秒以内に `tap` か `swipe` を **1 回**だけ実行できます。ほかの操作（`type`、`paste`、`press`、`elements`、`install`、`launch`）を実行すると、その `look` は無効になります。次に `tap` や `swipe` をするには、もう一度 `look` が必要です。
- `look` のあとにデバイスの向きが変わると、`tap` と `swipe` は拒否されます。変化は、デバイスが報告する向きか、画像の縦横から検出します。デバイスが向きを報告しない場合は、検出できる**とは限りません**。`tap` と `swipe` の座標は、直前の `look` が返した画像のピクセルで指定します。
- `type`、`paste`、`press` は、そのとき画面でフォーカスのあるものに作用します。`paste` を実行すると、デバイスは毎回「ペーストを許可」と尋ねます。
- 各ツールには、MCP の `readOnlyHint` と `destructiveHint` を付けています。読むだけのツールとしているのは、`devices` と `look` です。`elements` は、どちらでもありません。画面をスクロールさせることはありますが、何かを消すことはないためです。残りのツールは、破壊的な操作としています。押したものや入力した文字は、手で操作したときと同じように働きます。たとえば、タップで削除や送信をすることもあり、入力した改行は Return になります。`press` の `lock` はここから取り消せません。`launch` は実行中のアプリを先に終了させ、`install` はアプリを置き換えます。この印をどう扱うかはクライアントしだいで、実際のクライアントでの動きは確かめていません。
- 実行待ちの呼び出しは、始まる前に取り消されれば実行されません。すでに実行中の呼び出しは、最後まで実行されることがあります。MCP サーバーは接続を開いたまま保ち、保存した対応が変わったときや、接続が切れたときには、デバイスに接続し直します。
- `look` や入力で、動画のストリームが張られたままになったり、画面共有のセッションが表示されたりすることはありません。画面と入力を試している間、音楽は再生されたままでした。マイクや、そのほかの一部の操作については確かめていません。

## アプリのインストール

- `install` には、対象のデバイス向けにビルドした `.ipa` か、署名済みの `.app` ディレクトリを指定します。`roamrunctl` はコンパイルも署名もしません。
- `.app` ディレクトリは、デバイス上にその名前のまま一時的に置かれます。`.ipa` は、決まった 1 つの名前で置かれます。**1 台のデバイスに、同時に複数のインストールを実行しないでください。** コマンドどうしで調整する仕組みはありません。
- 中断されたインストールの残りは、次に `.app` をインストールするときに、可能な範囲で片づけます。コマンドは、転送するサイズと上限の時間を表示してから、結果を報告します。MCP のツールも、処理が終わってから結果を返します。

## `pair introduce` のオプションと結果

```text
roamrunctl pair introduce --host <host> --to <device> [--offer <line>] [--as <name>] [--deadline <secs>] [--on <address>]
```

- ホストでは、次のいずれかを実行しておきます。
  - `roamrunctl pair control --with <仲介マシン>`
  - `roamrun pair control --with <仲介マシン>`（RoamRun のアプリを起動しておく）
  - `roamrun pair xcode --with <仲介マシン>`（Xcode の Device Hub で待機しておく）
- どちらの側のコマンドを先に実行しても構いません。
- RoamRun を入れた Mac を、仲介マシンとして使うこともできます。その場合は `roamrun pair introduce --host <ホスト> --to <RoamRun に保存してあるデバイスの名前>` を実行します。ただし、仲介マシンが Mac で、ホストが `roamrunctl` の構成は、この文書を書いた時点では試していません。
- `--offer` は、Xcode のオファーを TCP 41830 で要求する代わりに、手で渡すためのオプションです。`--offer "$(ssh <離れた Mac> roamrun pair xcode)"` のように使います。ホストのポート 41830 が閉じている場合のためのものです。デバイス操作のペアリングには、これにあたるオプションはありません。
- `--as` は、ホストがデバイスを保存するときの名前を指定します。ホストは、その名前を拒否することがあります。Xcode のペアリングでは、その場合、表示されたデバイスの情報を `roamrun devices add <行> --as <別の名前>` で手動で追加できます。ホストが `roamrunctl` の場合は、ホスト側の `--as` が優先されます。
- `--on` は、仲介マシンがデバイスのネットワークに複数のアドレスを持つときに、使うローカルの IPv4 アドレスを指定します。指定しなければ、システムがデバイス宛ての通信に使うアドレスを選び、ほかの候補を表示します。
- Xcode の場合、ペアリングのコードはホストの Device Hub に表示されます。仲介マシンが作るものではありません。デバイス操作の場合は、関係するターミナルに表示されます。
- Remote Devices（デバイスの 設定 > 一般 > Remote Devices）を開いた Apple Vision Pro は、Mac に選ばれるのを待つ状態になります。このペアリングは RoamRun を入れた Mac どうしで行うもので、その形では動作を確かめてあります。こうしたデバイスに対して、Mac の `roamrun pair introduce` は、Mac 以外を `--host` に指定すると拒否します。Vision Pro と `roamrunctl` を組み合わせた動作は、確認していません。
- Xcode の場合、デバイスの情報が取得できれば、`roamrun devices add` に渡せる形で 1 行、**標準出力**に書かれます。状況や診断のメッセージは、**標準エラー**に出ます。

| 終了コード | 意味 |
|---|---|
| 0 | ホストが、ペアリングを保存したと報告した。`--offer` の場合は、Xcode のペアリングを試み、デバイスの情報を表示した。ホストには知らせていないので、表示された情報を、ホストで `roamrun devices add` を使って追加する必要がある |
| 1（デバイスの情報の行あり） | Xcode のペアリングを試みたが、ホストが保存を確認しなかった。ホストで手動で追加する |
| 1（デバイスの情報の行なし） | ペアリングが完了しなかった、デバイスが公開するサービスが見つからなかった、またはデバイス操作のペアリングが保存されなかった。標準エラーを確認する |
| 2 | コマンドラインの指定の誤り。サポートしていない `--mac` など（`--offer` なしで `--deadline` に 300 を超える値を指定した場合は 1） |

Ctrl-C を押したとき、ターミナルを閉じたとき、SSH のセッションが切れたときは、終了する前に Bonjour での公開をやめようとします。この動作は macOS で確認しています。Windows で確認したのは、Ctrl-C と、コンソールを閉じた場合です。

## うまくいかないとき

- **`roamrunctl` が見つからない：** Linux では、`~/.local/bin/roamrunctl` と指定して実行するか、`PATH` を直します。Windows では、展開したディレクトリの中の実行ファイルを指定するか、そのディレクトリを `PATH` に追加します。
- **Tailscale 上の名前が見つからない：** コマンドを実行するマシンで `tailscale status` を実行してください。iPhone に付けた表示名ではなく、Tailscale の DNS 名を使います。関係するマシンとデバイスがすべて、意図した tailnet でオンラインになっていることも確認してください。
- **`pair control --to` を実行しても、デバイスに表示されない：** 次の点を確認してください。
  - デベロッパモードが有効で、Wi-Fi に接続しているか
  - Tailscale が、ローカルの IPv4 で直接つながっているか
  - mDNS が通るか
  - ファイアウォールが、外からの接続を許可しているか

  コマンドの出力に、ポートと、通す必要のあるデバイスのアドレスが表示されます。
- **`pair control --with` が、コードが出る前に失敗する：** 仲介マシンから、操作マシンの TCP 41830 と、動的なペアリング用ポートに届く必要があります。`pair introduce` の出力に「デバイス自身の公開するサービスが見えない」と出る場合、そのデバイスはまだ一度もペアリングされていない可能性があります。先にデバイスと同じ Wi-Fi にあるマシンでペアリングしてください。
- **コードが拒否された：** 完了しなかったペアリングは保存されません。仲介をやり直し、新しく表示されたコードで試してください。離れた場所で待っているコマンドは、次の試行のために動き続けていることがあります。その場合は、出力にそう表示されます。
- **B で `roamrunctl devices` に何も表示されない：** 署名マシンで `roamrunctl sign phone --for <操作マシン>` を起動してください。TCP 41831 への接続の許可も必要です。どちらかのマシンにタグが付いているか、別の Tailscale ユーザーのものである場合は、操作マシンで `ROAMRUNCTL_SIGNER` を設定します。
- **MCP から、暗号化したデバイスを開けない：** `mcp` はターミナルで入力を求められません。MCP サーバーの環境変数に、`ROAMRUNCTL_PASSPHRASE_FILE` か `ROAMRUNCTL_PASSPHRASE_COMMAND` を設定してください。スキルを入れただけでは、MCP サーバーは起動しません。
- **それまで使えていたペアリングで接続できなくなった：** 同じマシンからデバイスをペアリングし直すと、デバイス上の以前のペアリングは置き換えられ、古いペアリング情報は拒否されるようになります。`roamrunctl devices remove <名前>` で古い情報を削除して、ペアリングし直してください。

## ビルドと確認

リポジトリを取得した状態で、`Rust/roamrunctl` で実行します。

```sh
cargo build --locked
cargo test
# macOS で。この Mac の LAN のアドレスを渡す
python3 scripts/local-check.py target/debug/roamrunctl "$(ipconfig getifaddr en0)"
```

この確認では、実際のデバイスとはペアリングしません。オファーは、試験専用の Bonjour サービス（`_rrtest._tcp`）で公開します。偽のデバイスは、実行中だけ、本物と同じ `_remotepairing._tcp` で LAN 上に公開されます。確認するのは、サービスの発見、想定外の相手の拒否、TCP の中継、デバイスの情報の作成、公開の後始末です。続けて、デバイス操作について、偽のホストとのやり取り、オファーの公開、中継、コードの表示、終了コード 0 を確認します。この Mac のポート 41830 と 53050 が空いている必要があります。

Mac 側の関連する実装は、`Sources/RoamRun/Introductions.swift`、`PairByName.swift`、`ControlIntroductions.swift` にあります。

## 試していない構成

これまでに、**iOS 27.0 の iPhone 15 Pro** を、Ubuntu 24.04（arm64）、ARM 版の Windows 11、macOS から数回動かしました。次のものは、この文書を書いた時点で、実機では確かめていません。

- iPad、上下逆さまに持ったデバイス、`roamrunctl` と Apple Vision Pro の組み合わせ（RoamRun を入れた Mac では、Vision Pro で動かしています）
- Mac を一度も使わない初期設定、Xcode で一度も準備したことのないデバイス、一度もペアリングしたことのないデバイス
- x86_64 のマシン、Avahi のない Linux、ufw 以外のファイアウォールのツール
- 複数のデバイスへの同時の署名、`ROAMRUNCTL_SIGNER` による指定
- RoamRun を入れた Mac を仲介マシンとし、`roamrunctl` を実行するマシンをホストとする構成
- MCP 経由の swipe、type、paste、install、launch（MCP を使わない形では確かめています）
- Windows での `pair control --with`、MCP、install、launch
- 待ち受けるアドレスのない、Tailscale のユーザースペースネットワーキング
- `--mac` から `--host` への変更後に、`pair introduce` を使って Xcode とペアリングする構成

セキュリティの考え方と制限の全体は、[SECURITY.md](https://github.com/mh-mobile/RoamRun/blob/main/SECURITY.md) を参照してください。
